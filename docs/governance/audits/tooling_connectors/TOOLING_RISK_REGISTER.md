# Tooling Risk Register — FrostGate Core

Covers every INSTALL NOW / PILOT / PLAN recommendation from the companion files, plus the HIGH RISK items that were explicitly rejected but are recorded here for visibility. Likelihood/Impact are qualitative (Low/Medium/High), consistent with the audit's read-only-first posture.

| # | Recommendation | Source | Risk | Likelihood | Impact | Mitigation | Residual risk | Owner role | Approval requirement |
|---|---|---|---|---|---|---|---|---|---|
| 1 | GitHub MCP (read-only) | CLAUDE_CODE_MCP | Token over-scoped beyond `Arescoreadmin/fg-core` (org-wide grant instead of repo-scoped) | Low | Medium (would expose other private org repos to the same session) | Use a fine-grained PAT or GitHub App installation scoped to this repo only; verify scope before first use | Low | Repo owner / Jason Cosat | Owner approval before token creation |
| 2 | Postgres MCP (local-only) | CLAUDE_CODE_MCP | Connection string misconfigured to point at Railway prod instead of local compose | Low | **High** (would expose regulated-industry tenant data to model context) | Hard-pin connection host at setup time; add an explicit startup assertion the host resolves to `localhost`/compose network, refuse to start otherwise; never store the prod `FG_DB_URL` value anywhere the MCP server config could reference it | Low, if the startup assertion is implemented as described | Repo owner | Owner review of the exact connection-string configuration before first use |
| 3 | Playwright MCP (local dev, seeded test tenant) | CLAUDE_CODE_MCP | Test credentials accidentally reused from a real client engagement, or a captured screenshot/DOM snapshot contains real tenant data if pointed at the wrong environment | Low | Medium | Use a clearly-synthetic seeded tenant (e.g., `demo`/`test-tenant` naming convention already used elsewhere per `scripts/seed_demo_decisions.sh`); never configure the MCP server with a URL that resolves to console.frostgate.ai or the portal's prod domain | Low | Engineering lead | None beyond normal dev-dependency addition review (standard PR review) |
| 4 | Vercel MCP (read-only, project-scoped) | CLAUDE_CODE_MCP | Vercel OAuth grant is org-wide by default rather than project-scoped; org-wide access would expose other Vercel projects/env vars beyond `console.frostgate.ai` | Medium (depends on what scoping the Vercel plugin actually offers) | Medium | Confirm project-level scoping is available before completing OAuth; if only org-wide scoping is offered, escalate to owner before proceeding rather than defaulting to broad access | Medium until scoping is confirmed | Repo owner | Owner approval before completing Vercel OAuth flow |
| 5 | Dependabot (security updates) | GITHUB_CI_ADDON | Automated PRs merged without review (if auto-merge is separately configured, which this audit does not recommend) | Low | Medium | Enable security-updates only, PR creation only, no auto-merge; require the same review process as any other PR | Low | Repo owner | None to enable (GitHub-native, reversible); standard PR review applies to resulting PRs |
| 6 | CodeQL (Python + JS/TS) | GITHUB_CI_ADDON | Requires GitHub Advanced Security license for a private repo — unbudgeted cost if enabled without confirming licensing | Medium | Low (cost/config risk, not security risk) | Confirm GHAS licensing status before enabling; start in non-blocking `report`-only mode on `api/`/`admin_gateway/` to bound noise before any blocking gate is added | Low once licensing confirmed | Repo owner (cost decision) + Engineering lead (rollout) | Owner approval (cost) before enabling |
| 7 | Trivy (container image scan) | GITHUB_CI_ADDON | False positives on base-image CVEs with no available fix (Alpine/Debian package advisories with no upstream patch yet) could block releases if made blocking too early | Medium | Low | Add as non-blocking first; build an ignore-list for accepted/unfixable base-image risk before promoting to a blocking gate | Low | Engineering lead | None (OSS, self-hosted/offline capable, no external account) |
| 8 | `npm audit` (console/portal/root) | GITHUB_CI_ADDON | Same false-positive-blocking risk as Trivy if made blocking immediately | Low | Low | Non-blocking first; review findings for a cycle before deciding on blocking | Low | Engineering lead | None |
| 9 | Coverage reporting (self-hosted `pytest --cov` artifact) | GITHUB_CI_ADDON | Adds CI time to an already-long critical path if not scoped carefully | Low | Low | Add `--cov` only to the `unit` job (already the longest-running lane regardless); keep as an artifact, not a blocking coverage-threshold gate, until a baseline is established | Low | Engineering lead | None |
| 10 | Sentry connector (contingent, prod-scoped, read-only) | PRODUCTION_OPERATIONS | Prod error events may contain tenant-identifying context (regulated-industry clients: healthcare/legal) in stack traces or breadcrumbs, which would then enter an AI model's context via the connector | Medium | **High** (potential PHI/PII exposure for a healthcare-vertical client) | Do not connect until (a) `SENTRY_DSN` is confirmed live via a startup assertion, and (b) Sentry's PII-scrubbing / `before_send` scrubber configuration is confirmed to strip tenant-identifying fields before events leave the application | Medium until both preconditions are independently verified — **do not treat this recommendation as approved until then** | Repo owner + whoever owns Sentry project configuration | Owner approval, contingent on documented PII-scrubbing verification |
| 11 | Auth0 Management API connector (deferred, read-only) | PRODUCTION_OPERATIONS | Auth0 logs contain login metadata (IPs, user agents, timestamps) for real end users across potentially all client tenants sharing the Auth0 tenant, not just FrostGate's own data | Low (deferred, not being installed now) | Medium if ever installed | Do not provision until a specific recurring debugging need is identified and scoped narrowly (e.g., `read:logs` only, time-boxed) | N/A — currently deferred | Repo owner | Owner approval required before any future provisioning |
| 12 | **Production Postgres / Redis access for any AI agent** | PRODUCTION_OPERATIONS | Direct exposure of regulated-industry, multi-tenant customer evidence data to an AI model's context window | Low (explicitly rejected in this audit) | **Critical** | **Reject.** No mitigation short of not doing it makes this an acceptable default; if ever revisited, it requires a separate, explicit founder/legal data-processing decision, not a tooling-audit approval | N/A — not recommended, and this audit does not have the authority to approve it even with mitigations | Founder / legal | Explicit founder + legal approval required; outside this audit's scope entirely |
| 13 | AWS Organizations/Config/Security Hub/CloudTrail native connector (product feature) | FROSTGATE_NATIVE_CONNECTOR_ROADMAP | Cross-account IAM role assumption is a materially higher-privilege credential model than anything in the current connector framework (which is entirely device-code/delegated-OAuth); a scoping mistake could grant broader-than-intended access into a client's AWS account | Medium (new pattern, no existing precedent to inherit safety properties from) | High (client production cloud infrastructure) | Require external-ID-scoped `sts:AssumeRole` with a minimal read-only IAM policy (`SecurityAudit` managed policy or narrower), isolate the new credential-storage code path behind its own security review before merge, do not reuse the existing OAuth token store schema without an explicit review of whether its encryption-at-rest and access-control properties suit a different credential class | Medium — inherent to expanding into a new cloud provider's credential model; manageable with the mitigations listed but not eliminable | Engineering lead + security reviewer | Dedicated security review required before merge (beyond standard PR review), given this introduces a new credential/privilege class into the connector framework |
| 14 | Jira/ServiceNow bidirectional remediation sync (product feature) | FROSTGATE_NATIVE_CONNECTOR_ROADMAP | This is FrostGate's first *write-capable, bidirectional* connector — every existing connector is read-only scan. A sync bug could create duplicate/conflicting tickets in a client's production ticketing system, or (worse) incorrectly mark a FrostGate finding as remediated based on bad sync state | Medium (new architecture, no precedent) | Medium (operational/trust impact on the client relationship, not a data-exposure incident) | Build conflict-resolution logic defensively (prefer "flag for human review" over "auto-resolve" on any sync ambiguity); do not allow the sync to auto-close a FrostGate finding without a corresponding verified evidence link, consistent with the existing remediation-effectiveness verification pattern (`services/remediation_effectiveness/`) | Medium — bounded by defensive design, not eliminated, because bidirectional sync with a third-party system is inherently harder to fully test than a read-only scan | Engineering lead | Standard PR review, but flag explicitly in review as the first write-capable connector — worth an explicit design review before implementation begins, not just at PR time |
| 15 | OneTrust/Archer/Drata/Vanta evidence-import connector (product feature) | FROSTGATE_NATIVE_CONNECTOR_ROADMAP | Not a data-security risk — a **strategic-positioning risk**: building toward a competitor's data model could be read as inconsistent with the explicit GRC-displacement narrative in `FOUNDER_DIRECTIVE.md` | N/A (not a security likelihood/impact) | N/A | Do not schedule engineering work until the founder makes an explicit call | N/A | Founder | Founder decision required before this even enters a PR sequence |
| 16 | Broad/write GitHub MCP, generic filesystem/semantic-search MCP, Gitleaks/TruffleHog, SonarCloud/Snyk, Renovate, OSSF Scorecard | Multiple files | Each rejected primarily for duplicating an existing better-tuned gate, or (SonarCloud/Snyk) for introducing an unreviewed third-party data-egress path for enterprise source code | Low (rejected, not being installed) | Varies — flagged as Medium-High specifically for SonarCloud/Snyk given the data-egress question | N/A — not recommended | N/A | Repo owner | Would require an explicit reversal of this audit's rejection, with a stated reason the existing gate is insufficient |
