# FrostGate Native Connector Roadmap

**Scope note (required separation):** This file covers **Category B only** — native connectors FrostGate should build *into the product* for customers to use during assessments and continuous monitoring. It does not cover developer/CI tooling used to build FrostGate itself (Category A — see `CLAUDE_CODE_MCP_RECOMMENDATIONS.md` and `GITHUB_CI_ADDON_RECOMMENDATIONS.md`).

Evidence base: `services/connectors/` (9 implemented connector families), `docs/CONNECTOR_CROSSREF.md`, `contracts/connectors/`, `api/connectors_*.py`, `SYSTEM.md` §1/§13 (target markets), `FOUNDER_DIRECTIVE.md` (competitive positioning, moat framing).

**Observation:** The entire authenticated-connector surface today is **Microsoft-stack-only** (6 of 6 authenticated connectors use MS Graph device-code auth). The 3 no-auth connectors and 4 AI-governance connectors are platform-agnostic. This is a deliberate, well-executed depth play on Microsoft 365/Entra (matches `SYSTEM.md`'s stated target market — community banking, healthcare, legal, govcon — verticals that skew heavily Microsoft 365 for productivity/identity). It also means **any client not on Microsoft 365 for identity gets meaningfully less coverage today**, which is the primary strategic gap this roadmap addresses.

## 2. Ranked Roadmap

Ranking criteria per the audit brief: fit with existing architecture, customer demand, evidence value, recurring-revenue potential, implementation effort, security risk, maintenance burden, competitive moat, assessment automation value, continuous-governance value, enterprise sales value.

| Rank | Connector | Target buyer | Evidence supported | Commercial value | Moat value | Complexity | Dependencies |
|---|---|---|---|---|---|---|---|
| 1 | **Okta (identity governance)** | Any client using Okta instead of Entra ID for SSO/identity | MFA coverage, privileged role assignments, app OAuth grants, guest/inactive account exposure — direct parity with the existing MS Graph Core + Entra Governance findings set | High — unblocks every non-Microsoft-identity client segment (a large share of tech-forward legal/fintech targets use Okta, not Entra) | Medium — extends the identity-governance depth story to a second IdP, widening addressable market rather than deepening an existing moat | Medium — Okta's API is REST/OAuth2 (client-credentials or SSWS token), no device-code-flow equivalent needed; the connector *pattern* (`services/connectors/entra_governance/runner.py`) is directly portable | None new — reuses `services/connectors/registry.py`, `services/connectors/policy.py`, idempotency framework (`idempotency.py`) already built for MS Graph connectors |
| 2 | **Microsoft Defender for Endpoint / Microsoft Sentinel (via Graph Security API)** | Existing MS 365 clients with Defender/Sentinel licensed | Endpoint threat detections, security incident data, Sentinel analytics-rule coverage — deepens the *continuous monitoring* (Tier 4, per `SYSTEM.md` §1 pricing table) story with real-time signal, not just point-in-time posture | High — directly serves the highest-margin tier ($100–250K+/yr "Autonomous" tier in `SYSTEM.md`) | High — turns FrostGate from a periodic-assessment tool into a continuous-signal aggregator for clients already paying for Defender/Sentinel, which is exactly the "continuous governance" differentiation `FOUNDER_DIRECTIVE.md` calls out against Vanta/Drata (who have no security-signal ingestion, only questionnaire automation) | Medium — uses the *same* MS Graph device-code/app-registration pattern already built (Security API is part of Graph), lower incremental effort than a net-new IdP integration | Requires `SecurityEvents.Read.All`/`SecurityAlert.Read.All` scopes on the existing app registration; reuses existing `services/connectors/msgraph/` client |
| 3 | **AWS Organizations + Config + Security Hub + CloudTrail (bundle)** | Govcon and fintech clients running AWS infrastructure | Cloud configuration posture (Config rules), aggregated findings (Security Hub), account/OU structure (Organizations), audit trail presence (CloudTrail enabled/retention) | High — govcon is an explicit target vertical (`SYSTEM.md` §13); FedRAMP/CMMC-adjacent clients expect cloud posture evidence, not just M365 identity posture | High — no direct competitor named in `FOUNDER_DIRECTIVE.md` (Vanta/Drata/OneTrust) offers *field-assessor-verified* cloud posture the way FrostGate's evidence-chain model would; this is a genuine moat extension, not just feature parity | High — cross-account IAM role assumption (`sts:AssumeRole` with an external ID) is a materially different and higher-risk auth model than the device-code pattern used everywhere else in the connector framework; requires new credential-storage and scoping work in `services/connectors/` | New: cross-account role-assumption credential flow, new entry in `contracts/connectors/policies/`, new RLS/tenant-scoping review for AWS credential storage (extend `services/connectors/oauth_store.py` pattern or build an equivalent) |
| 4 | **Google Workspace + Cloud Asset Inventory** | Clients on Google Workspace instead of M365; GCP-hosted clients | MFA/2SV coverage, admin role assignments, OAuth app grants (Workspace) mirroring the MS Graph Core finding set; asset inventory posture (GCP) mirroring AWS Config | Medium — smaller share of this platform's target verticals (community banking, healthcare, legal skew Microsoft) than Okta/AWS, but still a real segment | Medium — same "widen addressable market" logic as Okta, one tier lower priority because target-market fit is weaker | Medium (Workspace Admin SDK, OAuth2 service-account or domain-wide delegation) to High (GCP Asset Inventory, separate credential model) | Similar to Okta for the Workspace half; similar to AWS for the GCP half — recommend splitting into two separate PRs (Workspace first, GCP Asset Inventory second) rather than one bundle |
| 5 | **Jira / ServiceNow (remediation ticketing sync)** | Any client with an existing ticketing system for remediation ownership | Not a *scan* connector — a **bidirectional sync** connector: pushes FrostGate findings/remediation items into the client's existing ticket system and pulls status back, closing the loop with `services/remediation/`, `api/remediation_authority.py`, `services/remediation_effectiveness/` (already-built remediation workflow engine per migrations `0119`–`0121`) | Medium-High — this is a retention/stickiness play more than a net-new-evidence play: clients are far less likely to churn once their remediation workflow lives partly inside their existing ticketing tool | Medium — doesn't widen evidence coverage, but strengthens the "continuous, not one-time" narrative from `FOUNDER_DIRECTIVE.md` by making FrostGate operationally embedded in the client's day-to-day workflow | Medium — REST APIs on both sides, well-trodden integration pattern (webhook + polling), but requires new two-way sync/conflict-resolution logic not present in any existing connector (all current connectors are read-only *scan* connectors, not bidirectional sync) | New: webhook receiver infrastructure, sync-state model, conflict resolution — a genuinely new connector *class*, not a variant of the existing scan-connector pattern |
| 6 | **Slack / Microsoft Teams (alerting/notification)** | All continuous-monitoring-tier clients | Not evidence-collecting — delivers drift/finding alerts (`services/connectors/drift/alerts.py` already exists) into the client's existing chat tool instead of only the portal | Medium — improves perceived responsiveness of the "Autonomous" tier without new evidence work | Low-Medium — table-stakes for a continuous-monitoring product at this price point; doesn't widen the moat but its *absence* would be a competitive gap against Datadog/PagerDuty-adjacent expectations | Low — both platforms have simple incoming-webhook APIs; `services/connectors/drift/alerts.py` already has an alert-generation point to hook into | None new beyond a webhook-URL credential per tenant |
| 7 | **Microsoft Purview (DLP / data governance)** | Existing MS 365 clients, especially healthcare (HIPAA) and legal (privilege) verticals | Data classification/DLP policy coverage — extends the AI Data Access Mapping connector's story (`services/connectors/ai_data_access_mapping/`) from "what can AI tools access" to "how is sensitive data classified and protected at the source," a natural narrative pairing | Medium-High for the healthcare/legal verticals specifically | High for those verticals — directly reinforces the AI-governance moat asset (`FOUNDER_DIRECTIVE.md`'s "Customer-specific RAG corpus" and evidence-chain framing) with source-classification evidence, not just access-pattern evidence | Medium — same MS Graph/device-code pattern, additional scopes (`InformationProtectionPolicy.Read` is already requested by MS Graph Core per `docs/CONNECTOR_CROSSREF.md` — this connector deepens what's already partially scoped) | Reuses existing MS Graph client; low incremental credential/auth work |
| 8 | **CrowdStrike (EDR posture)** | Clients running CrowdStrike instead of/alongside Defender | Endpoint detection/response coverage, sensor health, detection counts — parallel to the Defender/Sentinel connector above for non-Microsoft-EDR shops | Medium — narrower addressable set than Defender given CrowdStrike is typically a larger-enterprise product, less common in this platform's SMB/mid-market regulated-industry target | Medium | Medium — CrowdStrike Falcon API is REST/OAuth2, well-documented, no unusual auth model | New credential type (Falcon API client ID/secret), new entry in connector registry |
| 9 | **Snowflake / data catalogs (data access inventory)** | Larger clients with a data warehouse, particularly for the AI-governance story (who/what can query sensitive data) | Extends AI Data Access Mapping (`services/connectors/ai_data_access_mapping/`) to structured-data access patterns, not just SaaS/AI-tool OAuth grants | Low-Medium near-term — most target-market clients (community banks, small-to-mid healthcare/legal) are less likely to run Snowflake than M365/AWS; better fit for a future upmarket move | Medium — plausible future moat extension for the AI-governance product line specifically, not urgent today | Medium (Snowflake's account/role/grant model is queryable via SQL, no unusual auth) | Depends on AI Data Access Mapping's existing data model being extensible to a new source type |
| 10 | **OneTrust / Archer / Drata / Vanta (evidence import / migration accelerator)** | Prospects currently using a competitor GRC tool who want to switch to FrostGate without re-entering existing control evidence | One-time import of existing control mappings/evidence metadata to reduce switching friction during a sales cycle | Medium, narrowly — this is a **sales-conversion tool**, not a recurring product feature; value is concentrated at the moment of a competitive displacement, which `FOUNDER_DIRECTIVE.md` explicitly frames as the strategic goal against these exact vendors | **Strategically ambivalent — flag explicitly for founder review, do not default to building.** Building an *integration with* a competitor sits oddly next to `FOUNDER_DIRECTIVE.md`'s explicit "GRC displacement" framing; it could either (a) lower switching friction and accelerate displacement, or (b) be read as legitimizing the competitor's data model as something worth preserving. This is a positioning call, not an engineering one. | Low-Medium (most of these vendors expose export APIs or at least CSV/JSON export) | None new technically; the open question is strategic, not architectural |
| 11 | **GitHub Enterprise / GitLab (code security posture)** | Clients with a software engineering function (fintech, some govcon) | Branch protection, secret-scanning enablement, dependency-alert posture — a SOC 2/ISO 27001 control-evidence source | Low-Medium — narrower fit than the top 6 given this platform's stated target verticals skew toward orgs *using* AI tools, not necessarily orgs *building* software at scale | Low-Medium — relevant mainly as this platform moves upmarket toward SOC 2-focused clients (already has SOC2/CMMC/ISO27001 playbooks per ROADMAP.md Phase 2 P2 items 19) | Low — both platforms have well-documented REST/GraphQL APIs and OAuth apps | None new |
| 12 | **Wiz / Palo Alto (CSPM/CNAPP)** | Larger cloud-native clients already running a dedicated CSPM tool | Would primarily *re-surface* findings Wiz/Palo Alto already generate, rather than produce net-new evidence | Low | Low — the AWS Config/Security Hub connector (rank 3) gives FrostGate first-party cloud-posture evidence without depending on the client already owning a separate CSPM license; building a Wiz/Palo Alto *importer* is redundant with that first-party path for most of this platform's target market | Medium (each has its own API/auth model) | N/A — **not recommended** ahead of the first-party AWS connector; revisit only for large-enterprise deals where the client already has Wiz/Palo Alto deployed and won't grant direct cloud-account access |

Deliberately excluded from ranking (no evidence of fit): Salesforce, Workday, ServiceNow-as-CMDB (distinct from ServiceNow-as-ticketing, rank 5), Jamf/Intune (Intune already covered via the existing Endpoint Inventory connector's MS Graph `DeviceManagementManagedDevices.Read.All` scope), Elastic/Splunk/Datadog (SIEM *export* targets, not evidence *sources* — better framed as an output/alerting integration alongside Slack/Teams at rank 6 if a client specifically requests it, not a standalone connector).

## 3. Recommended PR Breakdown & Sequence

Following this repo's existing convention (`services/connectors/<name>/{__init__.py,runner.py}` + `api/connectors_*.py` router entry + `contracts/connectors/policies/*.json` + a migration + a `docs/CONNECTOR_CROSSREF.md` update + tests):

1. **PR N — Okta connector (rank 1).** Lowest incremental complexity (device-code-flow precedent doesn't apply, but the REST/OAuth2 client-credentials pattern is simpler, not harder), highest immediate addressable-market widening. Ship first.
2. **PR N+1 — Defender/Sentinel via Graph Security API (rank 2).** Reuses the existing MS Graph client almost entirely; primarily new scopes + new finding types + new bridge logic. Second because it's the highest revenue-tier leverage for the lowest incremental engineering cost.
3. **PR N+2 — Slack/Teams alerting (rank 6).** Deliberately sequenced early despite lower rank because it is small, low-risk, and immediately increases perceived value of every connector shipped before and after it (every new finding type becomes more visible). Reuses `services/connectors/drift/alerts.py`.
4. **PR N+3 — AWS Organizations/Config/Security Hub/CloudTrail bundle (rank 3).** Split internally into at least two PRs given complexity: (a) cross-account credential/role-assumption infrastructure as its own reviewable unit (security-sensitive, deserves isolated review), (b) the actual Config/Security Hub/CloudTrail data-collection logic built on top of (a).
5. **PR N+4 — Microsoft Purview (rank 7).** Sequenced after AWS rather than before Google Workspace because it's a near-zero-incremental-cost extension of already-scoped MS Graph permissions and directly reinforces the AI-governance/healthcare-legal narrative already central to this platform.
6. **PR N+5 — Jira/ServiceNow bidirectional sync (rank 5).** Sequenced later because it requires new architectural capability (webhook receivers, two-way sync state) not present anywhere else in the connector framework — this should follow, not lead, so the team isn't building new infrastructure and a new integration surface at the same time.
7. **PR N+6 onward — Google Workspace, CrowdStrike, Snowflake, GitHub/GitLab** in roughly rank order, each re-evaluated against actual client-pipeline demand at the time (this audit's ranking reflects evidence available today, not committed sales data).
8. **OneTrust/Archer/Drata/Vanta import (rank 10) — do not schedule** until the founder makes an explicit strategic call on whether a migration-accelerator connector fits the displacement narrative or undercuts it.

Every PR in this sequence should carry the same "not standalone" architectural declaration this repo's `CLAUDE.md`/`ROADMAP.md` conventions require for field-assessment/connector modules, and should extend — not fork — `services/connectors/registry.py`, `services/connectors/policy.py`, and `services/connectors/idempotency.py` rather than introducing parallel infrastructure per connector.
